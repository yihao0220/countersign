# 第七项：从空金库完整初始化（已确认并实现）

日期：2026-10-07。用户在收到五段说明后回复“继续”确认；按此设计完成，操作和实际测试证据见 [初始化说明](../../INITIALIZATION.md)。以下问题描述保留实施前状态。范围为当前本地 CountersignDemo、初始化脚本及对应测试；不切换公链、不改变真实资金或生产身份验证边界。

## 当前功能链与证据

./local.sh start → local_runtime.deploy → 构造函数预置供应商 7、PO-101、首个 Agent、预算和每日上限 → 延迟授权第二个 Agent → 原页面付款。

构造函数不能创建空登记表：agent_/payout_ 非零、budget_ 为正、expiry_ 为未来时间才可部署；创建时直接登记供应商与 PO，首个 Agent 即刻获得权限。已有时间锁测试证明部署后的新增操作，未证明所有初始权限都经过时间锁。

## 方案选择

推荐保留原演示，并新增明确的空金库模式和独立初始化入口。完整流程由已存在的排队/等待/执行组成，没有免等待的 initialize 管理入口。

替代方案一：只用现有预置合约写初始化测试。改动少，但登记表仍非空，不能通过真正的空金库验收。

替代方案二：去掉预置构造函数，所有部署都强制从空开始。接口和原测试/教学流程需迁移，本轮不采用。

## 合约改动

- 保留构造函数原五参数及原有合法预置部署行为。五参数全部为零、部署附带资金也为零时，明确进入空模式；其余组合沿用原校验。仍仅允许 chain ID 31337。
- 空模式只确定部署者为固定 Owner：Agent 无授权、供应商/PO 数量为零、所有预算和付款用量为零、余额为零、paused=true。Owner 有管理权；无 Agent 能付款。
- 收到后续充值只改变余额，不登记供应商、授权 Agent、恢复付款或增加额度。
- 首批供应商、Agent、每日上限均使用现有 queueAddVendor、queueAgentAuthorization、queueLimitIncrease(DailyLimit)，等待 120 秒执行；采购单必须在其供应商实际登记后才能排队，随后独立等待 120 秒执行。恢复付款继续 queueResume → 等待 120 秒 → execute。
- 空模式没有首个预置 Agent，兼容 agent() 查询一直为零；授权是否有效仍查询 authorizedAgents，而不是 agent()。
- 供应商 7 经排队执行登记时，同步其兼容 payout 查询。PO-101 经排队执行创建时，同步 totalBudget/remainingBudget/totalSpent/poExpiry；此前这些查询为零。
- poExpiry 从构造时 immutable 字段变为仅在创建 PO-101 时设置的存储字段，查询签名保持；不新增修改截止时间入口。PO ID 不可重用，所以创建后截止时间仍固定。原预置模式的截止时间仍由构造函数确定。
- PO-101 保留原一次性预算的兼容口径，仅允许 periodDays=0。周期 PO 使用其他编号（示例 PO-102）。否则旧 remainingBudget / totalSpent 的累计扣账口径会与周期补额度冲突；本轮不重写旧口径。此限制对已有预置模式无新增影响，PO-101 本来已存在且为一次性。
- 降额、关闭、停用、撤销立即生效，恢复/提额需等待；付款原因编号、治理 execute/cancel 权限、重复标识、每日统计和转账回滚行为保持。

## 本地初始化流程

保留 ./local.sh start。新增 ./local.sh start-empty：部署空模式，完成时间锁初始化后再启动页面/后端。未自动停止或重启用户正在使用的服务；同一模式已运行则复用，不同模式已运行则提示用户先停止自己的实例。

初始化配置为当前无价值解锁账户：Owner、guarded/naive 两个 Agent、供应商 7 与 8、一次性 PO-101（供应商 7，500）、周期 PO-102（供应商 8，100，每 30 天）。全金库每日上限 200，充值 500。PO-101 截止为配置时刻后 30 天，PO-102 截止后 365 天，创建后均不能延期。预算是付款许可，500 的资金不保证能同时付完全部 PO。

1. 部署空模式：检查没有 Agent、供应商、PO、预算或资金，且暂停。
2. 排队两个供应商、两个 Agent、每日上限；等待后执行并检查回执及链上结果。
3. 供应商已登记后排队两个 PO 和恢复付款；再等待后执行。充值与登记独立，首次恢复也须等待。
4. 检查所有已配置字段、权限与状态，记录部署交易、初始化交易和模式，再开放本机页面。

初始化脚本使用 Anvil 推进两轮各 120 秒，不假装等待真实时间；新实例初始时钟偏移与两轮模拟相匹配，初始化后按墙钟节奏继续，后续页面申请仍完整等待 120 秒。所有模拟仅允许本机 Anvil；不得变成正式链跳过等待的实现。

每笔交易都核对回执成功、变更 ID 与最终状态，失败则不报告初始化成功、不启动可用页面。运行文件只写非秘密地址、交易和状态，留在已有 .runtime 忽略目录；不保存/输出任何私钥。

## 测试与验收

新增独立空模式合约测试和 init-demo，以及本地初始化脚本的隔离 Anvil 集成测试。

- 部署后真空：零登记、零授权、零预算/资金、暂停；非 Owner 不能新增配置，未授权付款回滚且不伪造 Blocked。半初始化配置与非本地链仍拒绝。
- 充值 500 后仍没有付款许可，等待不足 120 秒不能执行；到点没有自动生效，须执行交易。供应商尚未执行登记时不能创建其 PO。
- 依次配置供应商、Agent、每日限额、采购单和恢复；先取消首批供应商或 Agent/PO 申请，等待后旧 ID 仍不能执行，重新排队须重新等待。
- 完成后供应商 7 / PO-101 付 30，供应商 8 / PO-102 付 20，分别剩 470/80；金库 450、每日已付 50、累计已付 50，互用 PO 拒付且不串账。重复账单仍拒付。
- 初始化后关闭/停用立即阻止付款，周期边界不多付、取消不可执行等已有测试继续通过；空模式周期 PO 额外核对边界补额度不增加余额或清空历史。
- 空模式 PO-101 的查询、降/提额、关闭、改供应商 7 收款地址与旧入口一致；禁止周期 PO-101，允许周期 PO-102。创建后 poExpiry 不可被新 PO 或调额修改。
- 原预置模式全部已有合约测试保持通过，后端完整回归通过。重新生成 ABI/拒付常量，前端类型检查、构建及调用编码检查通过；合约运行代码大小检查不超过 EIP-170 限制。
- 初始化集成测试在独立随机端口启动 Anvil，核对空构造交易、所有初始化回执和 HTTP 付款结果，不修改正在运行的链。时钟偏移和两种启动模式的选择单独验证。
