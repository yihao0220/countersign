## 第二步：管理员修改收款地址

```bash
./test.sh timelock-demo
```

管理员提交新地址 → 等待 120 秒，期间旧地址仍有效 → 到期后发起执行 → 新地址生效。
管理员可在执行前取消；取消后不能执行，重新提交要重新等待。
演示使用测试虚拟机推进时间，不需要真的等待 120 秒，也不改变电脑时钟。

本地管理员 `owner` 是创建合约的地址，固定且与 Agent 分开。
仅管理员能调用 `queuePayoutChange(7, newPayout)` 和 `cancel(changeId)`。
按团队方案，任何人都能调用 `execute(changeId)`，但只能执行管理员已提交且到期的那项修改，不能选择其他地址。
到期不会自动修改，必须有人发起执行交易。

`payoutChanges(changeId)` 可查询新地址、最早执行时间和状态；
`pendingPayoutChange()` 可查询供应商 7 的待执行编号；其他供应商查 `pendingVendorPayoutChange(vendorId)`。
每家供应商同时只允许一项待执行地址修改，不同供应商互不覆盖。
每次提交使用新编号，已执行和已取消的记录不能重复使用。
提交、执行、取消分别产生 `PayoutChangeQueued`、`PayoutChangeExecuted`、`PayoutChangeCancelled` 事件。
修改地址不会重置预算或清空已付款记录。

## 第三步：紧急暂停与延迟恢复

```bash
./test.sh pause-demo
```

管理员调用 `pause()` → 立即停止付款 → 管理员调用 `queueResume()` 提交恢复 → 等待 120 秒 → 调用 `execute(changeId)` 恢复。
暂停时，已授权 Agent 的请求返回 `false` 并记录原因是 `Paused` 的 `Blocked` 事件，余额、预算和账单记录保持不变。
未授权地址仍然回滚，不产生虚假的拒付事件。
恢复到期后仍需要执行交易；演示使用测试虚拟机推进时间，不是真的等待或连接真实链。

只有管理员能暂停、提交恢复或取消恢复；任何人能执行管理员已提交并到期的恢复。
`paused()` 可查询当前是否暂停；`resumeChanges(changeId)` 可查询恢复的时间和状态；
`pendingResumeChange()` 可查询待执行恢复编号。
暂停、提交恢复、执行恢复、取消恢复分别产生 `Paused`、`ResumeQueued`、`ResumeExecuted`、`ResumeCancelled` 事件。
没有立即恢复的入口。取消恢复后仍保持暂停；重新提交恢复需重新等待完整的 120 秒。
已执行恢复不能重复使用来解除以后的一次暂停。

暂停只阻止付款。地址修改、取消变更和补充本地资金仍能进行，不会自动恢复付款或重新发放预算。
每家供应商的地址修改与全金库的恢复付款分别保存待执行记录，不相互覆盖。
已经暂停时再次调用 `pause()` 会拒绝；要阻止待执行的恢复，管理员使用 `cancel(changeId)`。

## 第四步：预算有效期

```bash
./test.sh expiry-demo
```

创建合约时设定预算截止时间，创建后固定。
截止时间前仍按正常规则检查付款；到达截止时间及之后，记录原因 `POExpired` 的 `Blocked` 事件，不转钱、不扣预算、不标记新账单已付。
到期不会自动发出事件，也不需要定时清理；在收到付款请求时检查当前区块时间。

构造函数现在需要五个参数：`(agent_, payout_, budget_, expiry_, dailyLimit_)`。
`expiry_` 为 `uint64`，表示 Unix 时间戳秒数，必须晚于创建合约的区块时间；零、当前或过去时间均拒绝。
`poExpiry()` 可查询固定的截止时间，没有延期入口。
默认测试用“创建时加 30 天”作为输入示例，并非合约写死 30 天；测试模拟跳到截止前一秒、恰好到期、到期后一秒。
充值、修改收款地址或恢复付款都不会延长有效期，也不会重新发放额度。
暂停检查仍优先；暂停且过期时先记录 `Paused`，恢复后继续拒付并记录 `POExpired`。

## 第五步：每日上限与 Owner 额度管理

```bash
./test.sh limits-demo
```

新演示初始总预算 500、每日上限 200。原有测试使用每日上限 500，保留原场景；两者都是构造参数，不是写死额度。
每天按 UTC 零点（北京时间 08:00）划分，按区块时间记账，不是最近 24 小时滚动窗口。
本演示只向 PO-101 付款，成功后增加 `totalSpent()` 和全金库 `spentToday()`；其他 PO 的付款记入各自账目及全金库 `totalPaid()`，转账失败全部回滚。
跨天重新计算当天用量，总预算、截止时间、历史付款标识不重置。

- `totalBudget()` 是初始 PO-101 的批准额度，`remainingBudget()` 等于该 PO 总额度减累计已付；不是全金库余额或全部 PO 的预算汇总。
- `dailyLimit()` 是每日上限，`spentByDay(day)` 保留 UTC 日期序号对应的历史用量。
- `decreaseLimit(kind, newLimit)`：仅 Owner，立即调低。总预算不能低于累计已付；每日上限可低于今日已付，后续付款拒绝。允许降至零。
- `queueLimitIncrease(kind, newLimit)`：仅 Owner，排队调高，120 秒后调用 `execute(changeId)`；任何人只可执行已批准内容。
- `kind` 为 `0`（总预算）或 `1`（每日上限）。每类最多一项待执行申请，分别与地址、恢复操作独立。
- `cancel(changeId)` 仅 Owner。立即降额也会取消同类待执行提额；取消后重新提交需完整等待。
- `LimitChangeQueued`、`LimitChanged`、`LimitChangeExecuted`、`LimitChangeCancelled` 记录治理动作。
- 超过每日上限产生 `Blocked`，原因 `DailyLimitExceeded`（编号 10），账目不变。原有拒付检查优先。

提高额度不会给金库充值，也不延长有效期。总预算 500、已付 100，改成 800 后剩余为 700。
每日上限 200、今天已付 150，降到 100 后，今天停止后续付款，不追回已付款。

## 第六步：Owner 管理 Agent 权限

```bash
./test.sh agents-demo
```

初始 Agent 在创建合约时授权；后续多个 Agent 可以共同申请付款，所有人共享金库、每日额度和账单历史，同一 PO 的预算也由所有 Agent 共用。

- `authorizedAgents(account)` 查询当前权限；`agent()` 仅保留创建时的初始地址，撤销后仍返回原地址，不代表当前有权限。
- `queueAgentAuthorization(account)` 仅 Owner：授权新地址或重新授权被撤销地址，等待 120 秒后使用 `execute(changeId)` 生效。
- 零地址、Owner 地址、已授权地址不能排队授权。每个地址最多一项待执行申请，不同地址互不覆盖。
- `revokeAgent(account)` 仅 Owner，立即撤销。若该地址有待执行申请，也一起取消，旧申请不能重新打开权限。
- `cancel(changeId)` 仅 Owner，可取消授权申请；重新排队必须等待完整时间锁。
- `agentAuthorizations(changeId)` 保存地址、最早执行时间和状态；`pendingAgentAuthorization(account)` 查询待执行编号。
- 事件为 `AgentAuthorizationQueued`、`AgentAuthorizationExecuted`、`AgentAuthorizationCancelled`、`AgentRevoked`。
- 撤销后申请付款回滚为 `UnauthorizedAgent`，不生成 `Blocked`，不会改变余额或账目。

授权不增加预算、不清空已付金额、不延长有效期，也不会解除暂停。撤销一个 Agent 不会暂停其他已授权 Agent。
本地演示：旧 Agent 付 100 → Owner 撤销 → 旧 Agent 被拒绝 → 新 Agent 等待后付 100 → 两人当日累计 200，再付 1 被每日上限拒付。

## 第九步：采购单关闭与预算管理


当前 `periodDays=30` 表示从 PO 执行生效时刻起，每 30 天恢复一份额度；不是每个自然月 1 日重置。`periodDays=0` 表示一次性额度。到期时间仍是独立且固定的付款截止时间。

演示向 30 天周期 PO 付 100，当期剩零，金库剩 900。下一 UTC 日期每日用量归零，但该 PO 仍拒付；周期结束前一秒也不能付。恰好满 30 天后，可用额度恢复为 100，金库仍为 900，旧账单仍因重复被拒绝。新周期再付 20 后剩 80，累计已付 120；下一周期恢复 100 而不是 180。即使跳过多个周期，仍只恢复一份 100。关闭后跨周期仍拒付，历史和余额保留。

独立测试还验证：周期恢复不会清空同一 UTC 日期的全金库已付；即使周期额度恢复，实际余额不足仍拒付；到期恰逢周期边界仍拒付；暂停和供应商停用不会被周期切换解除。额度恢复只增加付款许可，不会给金库充值。

## 第十一步：统一验收治理时间锁

```bash
./test.sh governance-demo
```

2026-10-07 逐项验收的第五项。本轮核对现有入口和执行分支，新增 GovernanceTimelock.t.sol 的 8 项测试与统一演示，核心合约未改。

以下 9 类部署后操作均等待 120 秒，统一使用 `execute(changeId)` / `cancel(changeId)`：

| 操作 | 排队入口 |
|---|---|
| 新增供应商 | queueAddVendor |
| 新增采购单 | queueAddPO |
| 修改收款地址 | queuePayoutChange |
| 恢复付款 | queueResume |
| 初始 PO-101 提额 | queueLimitIncrease(TotalBudget) 或 queuePOBudgetIncrease(101)，共用一项申请 |
| 全金库每日上限提高 | queueLimitIncrease(DailyLimit) |
| 新增或重新授权 Agent | queueAgentAuthorization |
| 提款到 Owner | queueWithdraw |
| 其他 PO 提额 | queuePOBudgetIncrease(poId) |

## 已实现

- 保留预置演示，另支持零配置空金库；空模式初始供应商、采购单、Agent、每日上限和恢复全部走时间锁。支持多供应商、多采购单和多个 Agent。
- 每家供应商可延迟修改收款地址或立即停用；PO 可延迟新增或立即关闭，各自预算独立，支持一次性和周期额度。
- Owner 可调低任意 PO 的预算，调高需等待时间锁，已付历史保留；PO-101 的旧入口兼容，每日上限由全金库共用。
- Owner 可延迟提款，只能转给固定 Owner；执行时再次检查实际余额，失败回滚。
- 仅当前已授权的 Agent 能申请付款；Owner 可以立即撤销。
- 管理员可立即暂停付款；恢复需管理员提交，并等待时间锁后执行，可在执行前取消。
- 检查供应商、地址、采购单、固定预算截止时间、非零金额、剩余预算、重复标识、实际余额。
- 正常付款更新账目并记录 `Paid`；规则不符返回 `false` 并记录 `Blocked`。
- 未授权调用、重复进入付款流程、实际转账失败会回滚。
- 转账失败不会消耗预算，也不会把账单错误标为已付。

后端接入时，必须解析 `Paid` / `Blocked`，不能把交易执行成功直接等同于付款成功。
本版本的拒付原因编号已固定为本地 v1 约定；不声称团队已批准正式接口。

## 明确的边界

- 仅可部署到 chain ID `31337`；这只是防误用限制，不是安全认证。
- 新增供应商/PO、提款、改地址、恢复、提额及 Agent 授权等待 120 秒；默认预置模式初始设置未经时间锁，空模式完整登记需两轮等待。没有 Owner 交接。
- PO 截止时间不可延期，停用/关闭不能重新打开，编号不重用。PO-101 只允许一次性，其他 PO 支持周期；周期补额度不增加资金。没有 ERC-20。
- 本次新增本机交易发送模块与页面联调；尚无本项目公链部署或真实浏览器钱包签名验证。
- 提款固定到 Owner，不能自选收款人；不要用真实资金运行或直接移除链限制上线。
- `invoiceHash` 只防止同一个标识重复付款，不能证明账单真实；不同标识仍能消耗批准预算。
- 本地测试通过不代表审计通过，也不代表 BOT Chain 或 USDT 兼容性已验证。
